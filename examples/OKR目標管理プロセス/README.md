# 例: OKR・目標管理プロセス(架空 / IT 企業ケース)

このフォルダは、business-flow-architect の **リファレンス実例(IT 企業版)** です。AI が業務記述書 + drawio + 課題発生ポイント分析を生成するときに、「**IT 企業のヒアリングならこの粒度・密度で書く**」基準として参照します。

## このサンプルが示す要素

- ✅ P-001〜P-008 の 8 プロセス(時系列順、OKR ライフサイクル全体)
- ✅ F-001〜F-006 の 6 ファイル / データ
- ✅ S-001〜S-005 の 5 システム連携(Slack / Notion / Meet / Jira+GitHub / タレントパレット)
- ✅ C-001〜C-006 の 6 課題発生ポイント
- ✅ 自社プロダクトでの解決可能性判定(✅ × 3 / ⚠️ × 2 / ❌ × 1 の誠実な配分)
- ✅ **6 レーン構成**(メンバー / EM / プロダクト本部長 / 人事マネージャー / 社内システム / エンジニアツール)— 使わないレーンは削除して詰めた
- ✅ 通常フロー(実線)+ システム連携(破線)+ 並行処理(P-003/P-004/P-005 は半期内継続)
- ✅ 課題吹き出し(C-XXX)を該当プロセスの近くに配置

## IT 企業ケースとして見せるもの

経費精算プロセス(オペレーション系)とは異なる、**IT 企業特有の論点**:

| 観点 | IT 企業ケースの特徴 |
|---|---|
| 評価の難しさ | エンジニア / クリエイティブの数値化困難。営業 KPI が無いので「目標の立て方」自体がハードル |
| リモート前提 | フルリモート + Slack 中心 → 本音 / 温度感の不可視 = 退職予兆を取り逃す |
| 1on1 文化 | 月次 1on1 + Notion AI 録音は当たり前。**だが形骸化**(テンプレなし、録音しても活用されない) |
| スプリント運用 | Jira / GitHub でスプリント管理。**OKR と日々のスプリント業務が乖離** |
| ツール文化 | Slack / Notion / GitHub / Google Meet 多用、新しいツールへの抵抗感は低い |
| 制度の流動性 | スタートアップ特有、半期ごとに評価指標が変動 → フォーマット浸透前に陳腐化 |

## AI への指示(SKILL.md / prompts 経由で参照)

IT 企業のヒアリングを処理するとき、AI は本サンプルを開いて以下を学習する:

1. **エンジニア組織特有の用語の使い方**(EM / プロダクト本部長 / スプリント / Notion AI)
2. **C-XXX の根本原因カテゴリ** — 「人 / プロセス / システム / 文化」の中でも「文化」(リモート文化、評価文化、ツール文化)が多めになるパターン
3. **解決可能性の誠実な配分** — ✅ ばかりにせず、⚠️ や ❌ もちゃんと出す
4. **退職予兆候補メンバーの言及** — 「最近 Slack 投稿減少」「半期目標を立てた後ほぼ見ていない」など、定量シグナルから推測する書き方
5. **複数の意思決定者の関係性** — EM / 本部長 / 人事マネージャー の役割分担を業務記述書の「実施者」列で書き分け

## 利用条件

この実例は、**学習目的の参照** に使うことを想定しています。
**マスキング解除・再配布・SNS への転載** は禁止です(架空ケースですが、リアル感が強いため誤認回避目的)。
