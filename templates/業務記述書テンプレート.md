# 業務記述書テンプレート

Claude Code が ① 業務記述書を生成する際の出力フォーマット。プロセス番号付きフロー + 課題発生ポイント分析 (C-XXX) をセットで持つ。

---

## 出力ファイル名規約

```
./業務フロー/[プロセス名]_業務記述書_v[版数]_[YYYYMMDD].md
```

例: `./業務フロー/メンバー状況把握_業務記述書_v1.0_20260527.md`

---

## 採番ルール(必読)

| 種類 | 形式 | 採番基準 | 例 |
|---|---|---|---|
| 業務プロセス全体のコード | `BP-XXX` | プロジェクト内で 1 つの業務フローに 1 つ | BP-EXPENSE-001(経費精算)、BP-HIRING-001(採用) |
| 個別プロセス | `P-XXX` | 時系列順 | P-001, P-002, ... |
| ファイル・データ | `F-XXX` | 使用順序(同一ファイルが複数 P で使われるなら最初の使用順) | F-001, F-002, ... |
| システム連携 | `S-XXX` | 実行順序 | S-001, S-002, ... |
| 課題発生ポイント | `C-XXX` | 課題が見えた順序 | C-001, C-002, ... |

業務記述書と drawio で **P/F/S/C 番号は完全一致** させる。

## 2. プロセス詳細

| プロセス番号 | プロセス名 | 実施者 | 活動内容 | 使用証憑 | 作成証憑 | ファイル番号 | システム連携 | 前工程依存 | 後工程依存 | 備考 (⚠️ 課題発生ポイント) |
|---|---|---|---|---|---|---|---|---|---|---|
| P-001 | [プロセス名] | [部門・役職] | [活動内容] | [入力] | [出力] | F-001 | - | - | P-002 | **⚠️ C-001 [課題内容を 15 文字]** |
| **P-002** | **[判断名]**(ひし形) | [承認者] | [判断基準] | F-001 | 承認結果 | - | - | P-001 | **承認時: P-003 / 差戻し時: P-001** | - |
| P-003 | [プロセス名] | [部門・役職] | [活動内容] | F-001 | F-002 | F-002 | S-001 | P-002 (承認時) | P-004 | - |
| P-004a | [並行処理 A] | [担当 A] | [活動内容] | F-002 | F-003a | F-003a | - | P-003 | P-005(P-004b と並行 → P-005 で合流) | - |
| P-004b | [並行処理 B] | [担当 B] | [活動内容] | F-002 | F-003b | F-003b | - | P-003 | P-005(P-004a と並行 → P-005 で合流) | - |
| P-005 | [合流処理] | [担当] | [活動内容] | F-003a, F-003b | F-004 | F-004 | - | P-004a, P-004b | - | - |
| ... | | | | | | | | | | |

**記載ルール:**

- プロセス番号は **時系列順** (P-001, P-002, ...)
- 課題発生ポイントは備考欄に **⚠️ C-XXX [要約 15 文字]** で記載
- **判断ひし形(P-XXX)の後工程依存は "承認時: P-X / 差戻し時: P-Y" の形式で書く**(分岐先を明示)
- **並行処理がある場合は、P-XXXa / P-XXXb のようにサフィックスを付けて、後工程依存に「(P-XXXa と並行 → P-Z で合流)」と明記**
- 「実施者」は部門 + 役職(例: 経理部 担当者、経理マネージャー)。可能なら個人名(マスキング可)も追記

## 3. ファイル・データ一覧

| ファイル番号 | ファイル名 | 種類 | 形式 | 保管場所 | 保持期間 | 作成プロセス | 使用プロセス | 備考 (課題への逆参照) |
|---|---|---|---|---|---|---|---|---|
| F-001 | [ファイル名] | 帳票 | Excel/PDF | [場所] | 7 年 | P-001 | P-002, P-003 | ⚠️ 紛失多発 (C-001) |
| F-002 | [ファイル名] | データ | CSV/DB | システム | 7 年 | P-003 | P-004 | - |
| ... | | | | | | | | |

**採番:** 使用順序、同一ファイルが複数 P で使われるなら最初の使用順を採用。

**備考欄ルール:**

- ファイルに紐づく **課題発生ポイント (C-XXX) を逆参照** で書く(例: `⚠️ 紛失多発 (C-001)`)
- 特記事項(電子署名付き、暗号化保存、自動バックアップ)も併記

## 4. システム連携

| 連携番号 | システム | 連携内容 | 頻度 | 実行プロセス | タイミング | 備考 |
|---|---|---|---|---|---|---|
| S-001 | [システム A → B] | [データ内容] | リアルタイム / 日次 / 月次 | P-002 | プロセス開始時 / 終了時 | API 連携、自動 / 手動 |
| ... | | | | | | |

**記載ルール:**

- リアルタイム連携か、バッチ(日次/月次)か、手動か を明示

- エラー時の処理(リトライ / 手動介入)があれば備考に

## 🆕 5. 課題発生ポイント分析

ヒアリング相手の業務に潜む「課題発生ポイント」を C-XXX 番号付きで整理。

> **本セクションは独立ファイル `[プロセス名]_課題発生ポイント分析_v1.0_YYYYMMDD.md` としても出力する。**
> 独立ファイル時は §5.0「エグゼクティブサマリー」+ §5.5「顧客像推測」+ §5.6「提案論点」を必ず追加。

### 🆕 5.0 エグゼクティブサマリー(独立ファイル時必須)

ヒアリングから抽出された課題を 1 段落で要約し、**自社プロダクトの提案ターゲットを 1 行で出す**。

```
本ヒアリングから X 件の課題発生ポイント (C-001〜C-XXX) が抽出された。深刻度の高い N 件
(C-XXX, C-XXX) が業務全体のボトルネックを形成している。

| 視点 | 数値 |
|---|---|
| 抽出された課題数 | N 件 |
| 深刻度「高」の課題 | N 件 (C-XXX, C-XXX) |
| 自社プロダクトで ✅ 解決可能 | N 件 (C-XXX, C-XXX, C-XXX) |
| 自社プロダクトで ⚠️ 間接的のみ | N 件 (C-XXX, C-XXX) |
| 自社プロダクトで ❌ 不可 | N 件 |

→ **自社プロダクトの提案ターゲットは C-XXX + C-XXX のセット**。
   この組み合わせで顧客が感じている工数ロスのほぼ全てを解消できる。
```

### 5.1 課題サマリー

| 課題番号 | プロセス番号 | 課題内容 | 深刻度 | 根本原因のカテゴリ | 自社で解決可能? |
|---|---|---|---|---|---|
| C-001 | P-001 | [課題内容] | 🔴 高 / 🟡 中 / 🟢 低 | 人 / プロセス / システム / 文化 | ✅ 可能 / ⚠️ 間接的 / ❌ 不可 |
| C-002 | P-003 | [課題内容] | 🟡 中 | プロセス | ✅ 可能 |
| ... | | | | | |

### 5.2 根本原因の深掘り

#### C-001: [課題タイトル] 🔴 高

- **発生プロセス:** P-001
- **ヒアリングからの引用:**
  > 「[ヒアリングで出てきた具体的な発言、逐語引用]」
  > 「[補足の発言、複数行可]」
- **根本原因の構造:** [なぜそうなっているのかの構造分析、箇条書き可]
- **発生頻度:** [いつ・どれくらい / 月 N 件 = X% など定量化]
- **ビジネスインパクト:** [何が起きるか、影響範囲]
- **自社プロダクトでの解決:** ✅ **可能(優先度: 高)**
  - [必要な機能の説明]

#### C-002: [課題タイトル] 🟡 中
- (同じフォーマットで継続)

### 5.3 自社プロダクトでの解決可能性マトリクス

| 課題番号 | 課題 | 自社で解決可能? | 必要な機能 | 優先度 |
|---|---|---|---|---|
| C-001 | [課題] | ✅ **可能** | [必要な機能の具体] | 🔴 高 |
| C-002 | [課題] | ⚠️ 間接的 | [補助的に貢献する範囲] | 🟡 中 |
| C-003 | [課題] | ❌ 不可 | (対象外) | - |

**判定基準:**
- **✅ 可能** — 自社プロダクトのコア機能で **直接** 解決できる
- **⚠️ 間接的** — 関連する機能で **部分貢献** はできるが、直接の解決にはならない
- **❌ 不可** — 自社プロダクトの守備範囲外

### 5.4 次の検証アクション

- [ ] **追加ヒアリングで深掘り**: [具体的な項目]
- [ ] **プロトタイプで検証する機能**: [機能名]
- [ ] **提案シナリオに含める論点**: [論点]

### 🆕 5.5 顧客像推測(独立ファイル時必須)

ヒアリング相手の組織を推測し、営業提案で使える情報に整理する。

```
- **業種**: [業界]
- **規模**: [従業員数 / ARR 推測]
- **経営オペレーション成熟度**: 低 / 中 / 高(根拠を1文)
- **自社プロダクトの受容性**: 低 / 中 / 高(根拠を1文)
- **意思決定者**: [ヒアリング相手の役職 + 上位決裁者の推測]
- **稟議承認者**: [CFO / 社長 等の推測]
- **想定 ACV**: [月額 × 12 ヶ月 + 初期 = 年額の試算]
- **競合**: [現在使っているツール、検討対象]
```

### 🆕 5.6 提案論点(独立ファイル時必須)

商談に持っていく具体的な論点を整理。

```
**定量効果(金額換算)**:
- 工数削減: N 時間 / 月 × 12 ヶ月 = X 時間 / 年
- 時給 Y 円換算で **Z 万円 / 年** のコスト削減
- リスク削減(税務 / 監査 / 法令)があれば定量化

**誠実な範囲限定**:
- 「C-XXX は自社プロダクトでは解決しません」と先に伝える(失う信頼を防ぐ)
- 「C-XXX + C-XXX のセット解決」にフォーカスして提案

**検証コミット**:
- 「N 週間以内に MVP / PoC を見せます。判断はそれを見てから」と提案
```

## 補足: 業務記述書 ⇔ drawio の整合性チェック

Claude Code が業務記述書を生成した後、drawio 図と以下の整合性を自動チェックする。

| チェック項目 | 業務記述書側 | drawio 側 |
|---|---|---|
| プロセス番号 | §2 の P-XXX | 角丸四角 / ひし形のラベル |
| ファイル番号 | §3 の F-XXX | 付箋(shape=note)のラベル |
| システム連携番号 | §4 の S-XXX | 破線エッジのラベル |
| 課題発生ポイント番号 | §5.1 の C-XXX | 吹き出し(shape=callout)のラベル |
| **判断ひし形の分岐先** | §2 の「承認時: P-X / 差戻し時: P-Y」 | drawio の "承認" / "差戻し" ラベル付きエッジ |
| **並行処理の合流先** | §2 の "P-X で合流" 記載 | drawio の複数エッジが同一プロセスに集まる構造 |

すべて一致しないと、Claude Code がレポートで警告を出す。
